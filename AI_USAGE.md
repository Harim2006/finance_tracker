## Key Concepts I Understand

### 1. How Overspend Rules Work
The `record_transaction()` method in budget_domain.py checks the envelope's `overspend_rule` before recording a transaction. If the rule is 'stop' and the new balance would be negative, it returns None to reject the transaction. If the rule is 'borrow', it allows the transaction even if it makes the balance negative. The logic is: `if new_balance < 0 and envelope['overspend_rule'] == 'stop': return None`.

### 2. How Monthly Rollover Works  
The `execute_monthly_rollover()` method loops through all envelopes. For each one, it calculates how much was spent this month using `SUM(amount)` from the transactions table filtered by month. It saves this to `envelope_history` for record-keeping. Then it updates the envelope's `current_balance` by adding the `monthly_allocation` to whatever is left, so: `new_balance = current_balance + monthly_allocation`. This means unspent money carries over.

### 3. How Bill Recurrence Calculation Works
The `_calculate_next_occurrence()` method in bill_domain.py uses the `python-dateutil` library's `relativedelta` class. For monthly bills, it does `current_due + relativedelta(months=1)` which correctly handles month boundaries (e.g., Jan 31 → Feb 28). For yearly bills, it's `relativedelta(years=1)`. The method looks at the bill's `frequency` field and applies the appropriate time delta. After calculating, it updates the bill's `next_due_date` column and creates a new unpaid record in `bill_payments`.

### 4. How Auto-Categorization Works
The `auto_categorize_transaction()` method queries the `category_rules` table ordered by priority (highest first). It lowercases the merchant name and checks if each rule's `merchant_pattern` appears in it using `if rule['merchant_pattern'].lower() in merchant_lower`. The first match wins and returns that rule's `envelope_id`. This allows transactions from "Walmart Supercenter #123" to automatically match the "walmart" pattern and go to the Groceries envelope.

### 5. How the Fake Bank API Works
The `/api/bank/transaction` route receives a POST request with merchant and amount. It calls `auto_categorize_transaction()` to find which envelope the transaction should go to. If a match is found, it calls `record_transaction()` to deduct the amount from that envelope's balance. This simulates what would happen if our app was connected to a real bank API that sends us transaction data when a purchase is made.

### 6. How Flask Routes Connect to Business Logic
Flask routes (in app.py) are thin wrappers. For example, `/envelopes/create` extracts `name`, `monthly_allocation`, and `overspend_rule` from the request, then calls `budget_manager.create_envelope()` which does the actual work (validates, inserts to database). The route just handles HTTP concerns (parsing request data, returning JSON or redirecting) while the domain manager handles business logic (calculations, rules, database operations). This separation makes testing easier - we can test the domain logic without HTTP.

### 7. How Coverage Measurement Works
The coverage tool (`coverage.py`) instruments our Python code to track which lines are executed during tests. When we run `coverage run -m unittest discover`, it runs all tests and records which lines in each file were hit. Then `coverage report --include="budget_domain.py,bill_domain.py"` filters the report to only show those two files, giving us the percentage of lines tested. We exclude app.py and templates because they're thin wrappers and hard to unit test (would need Flask test client, which tests integration not logic).

## What I Would Explain in the Comprehension Check

If asked to explain on paper with no notes:

**Q: How does the 'stop' overspend rule work?**  
A: "In budget_domain.py, the record_transaction method gets the envelope from the database and calculates new_balance = current_balance minus amount. If new_balance is less than zero AND the envelope's overspend_rule column is 'stop', it returns None to reject the transaction. Otherwise it inserts into the transactions table and updates the envelope's current_balance. The 'stop' rule prevents spending more than you have."

**Q: How does monthly rollover work?**  
A: "execute_monthly_rollover loops through envelopes. For each one, it sums the amounts from the transactions table for the current month to calculate spent. It saves this to envelope_history. Then it updates current_balance = current_balance + monthly_allocation, so leftover money carries over and new budget is added. It uses strftime('%Y-%m') to filter transactions by month."

**Q: How is the next bill due date calculated?**  
A: "_calculate_next_occurrence in bill_domain.py looks at the bill's frequency. For monthly, it uses python-dateutil's relativedelta(months=1) to add one month to current_due_date. For yearly it's relativedelta(years=1). relativedelta handles edge cases like month-end dates correctly. After calculating, it updates the bills table's next_due_date column and creates a new bill_payments record with status='unpaid'."

**Q: How does the fake LLM work?**  
A: "FinanceLLMAnalyzer in llm_analyzer.py uses pattern matching, not a real AI. analyze_and_answer converts the question to lowercase and checks if keywords like 'overspending' or 'afford' are present. Based on which keyword is found, it calls different methods like _analyze_overspending or _assess_affordability. These methods query the context dictionary (which has envelopes, bills, transactions data) and build response strings. For affordability, it uses regex to extract the dollar amount from the question, sums envelope balances, subtracts upcoming bills, and compares to the requested amount."
